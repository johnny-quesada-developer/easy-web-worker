## Keep the logic out of the worker file

The methods of a worker are ordinary functions. Put them in their own module, and let the worker file only wire
them.

## Replace the worker in unit tests

Test runners such as Vitest and Jest run in Node or jsdom, where `Worker` does not exist. Code that uses a worker
should receive it, so a test can hand it a fake one. The type of the worker keeps the fake honest.

<CodeBlock code={fakeClient} lang="ts" title="format.test.ts" />

## Cover the real thing in a browser

What the unit tests cannot see is the thread boundary itself: structured clone, transferable objects, real
cancellation timing, the worker file your bundler produces. Cover those with a browser test.

```ts
import { test, expect } from '@playwright/test';

test('computes in a worker', async ({ page }) => {
  await page.goto('/');
  await page.getByRole('button', { name: 'Run in a Worker' }).click();

  await expect(page.getByTestId('worker-result')).toHaveText('39,088,169');
});
```

<Callout type="note" title="How this library is tested">
  The package runs its unit suite against the source and against the built files, plus a Playwright suite with
  real Workers in Chrome. The examples on this site are part of that: they run against the built package.
</Callout>
